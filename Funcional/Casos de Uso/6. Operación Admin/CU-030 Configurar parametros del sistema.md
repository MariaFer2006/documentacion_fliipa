### CU-030: Configurar parámetros del sistema

![Diagrama de caso de uso CU-030](imagenes/diagrama_CU-030.svg)

| Campo | Detalle |
|---|---|
| **Actores** | Administrador con permiso de edición de configuración (Sys Admin / Core Admin); cualquier administrador autenticado (consulta de solo lectura). |
| **Descripción** | El administrador consulta y, si tiene el permiso correspondiente, edita los parámetros generales del sistema almacenados como registros `nombre: valor JSON` (fechas de corte, tasa de interés diaria, tasa de mora, plan de pagos, cargos aplicables, entre otros), que las calculadoras de crédito y planes de pago consumen en vivo. |
| **Precondiciones** | El administrador tiene sesión activa en el panel. Los settings ya existen (fueron sembrados previamente); el sistema no permite crear settings nuevos desde esta pantalla, solo editar el valor de los existentes. |
| **Flujo principal** | 1. El administrador entra a "Configuración" desde el menú lateral (sección Core).<br>2. El sistema lista todos los settings ordenados alfabéticamente por nombre, con su identificador, descripción, valor en formato JSON y fecha de última actualización.<br>3. El administrador edita el valor JSON de un setting en el textarea correspondiente (por ejemplo, `cutoff_dates` o `daily_interest_rate`).<br>4. El administrador presiona "Guardar".<br>5. El sistema valida en el navegador que el texto sea JSON válido; si lo es, envía la actualización al backend.<br>6. El backend actualiza el registro y responde con el nuevo valor.<br>7. El sistema refresca la lista mostrando el valor y la fecha de actualización más recientes. |
| **Flujos alternativos / excepciones** | A1. El administrador no tiene el permiso "Editar configuración": el campo de valor se muestra en modo solo lectura y el botón "Guardar" permanece deshabilitado.<br>A2. El JSON ingresado es inválido: el sistema muestra la alerta "JSON inválido" y no envía la petición.<br>A3. El nombre del setting no existe en el backend: el sistema responde 404 y no aplica el cambio.<br>A4. No se envía un valor en la petición: el sistema responde 400 ("value is required"). |
| **Postcondiciones** | El valor del setting queda actualizado en la base de datos y es consumido de inmediato por los servicios que lo leen en vivo (por ejemplo, el cálculo del plan de pagos y la tasa efectiva anual en `getRedemptionCreditSettings`), sin necesidad de reiniciar ningún servicio. La acción (éxito o falla) queda registrada en el log de auditoría del panel. |
| **Reglas de negocio** | Cada setting se identifica por un nombre único (`cutoff_dates`, `daily_interest_rate`, `overdue_interest_rate`, `payment_plan_config`, `payment_charges`). `cutoff_dates` define los días de corte válidos (`cutoffDates`), el día de corte por defecto (`defaultCutoffDate`) y el umbral en días (`thresholdDays`) usados por la calculadora de plan de pagos diario. `daily_interest_rate` y `overdue_interest_rate` son las tasas diarias vigente y de mora, base del cálculo de intereses y de la tasa efectiva anual mostrada al cliente. Toda modificación exitosa o fallida queda registrada en auditoría. |

| **Estado en plataforma** | **Implementado.** `GET /settings` y `PUT /settings/:name` (`settings.controller.ts`, `settings.service.ts`) están activos y la pantalla `apps/admin/src/app/settings/page.tsx` los consume. **Hallazgo técnico:** la ruta `PUT /settings/:name` solo exige `authenticate`; no aplica ningún middleware de permisos en el backend, por lo que el control de quién puede editar (permiso `core:update-setting`) hoy solo existe en el frontend. Se recomienda reforzar esta validación también del lado del servidor, dado que estos parámetros afectan directamente el cálculo de intereses y fechas de corte de todos los créditos activos. |
