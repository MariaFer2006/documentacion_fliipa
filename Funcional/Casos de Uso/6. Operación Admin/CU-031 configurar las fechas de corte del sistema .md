### CU-031: Configurar las fechas de corte del sistema

![Diagrama de caso de uso CU-031](imagenes/diagrama_CU-031.svg)

| Campo | Detalle |
|---|---|
| **Actores** | Administrador con permiso de edición de configuración (Sys Admin / Core Admin); cualquier administrador autenticado (consulta de solo lectura). |
| **Descripción** | El administrador consulta y, si tiene el permiso correspondiente, edita los días de corte válidos, el día de corte por defecto y el umbral de días usados para asignarlos, parámetros que la calculadora del plan de pagos diario consume en vivo. |
| **Precondiciones** | El administrador tiene sesión activa en el panel. El setting `cutoff_dates` ya existe (fue sembrado previamente); el sistema no permite crear settings nuevos desde esta pantalla, solo editar el valor existente. |
| **Flujo principal** | 1. El administrador entra a "Configuración" desde el menú lateral (sección Core).<br>2. El sistema muestra el setting `cutoff_dates` con su valor en formato JSON (`cutoffDates`, `defaultCutoffDate`, `thresholdDays`) y su fecha de última actualización.<br>3. El administrador edita el valor JSON (por ejemplo, agrega un nuevo día de corte a `cutoffDates`).<br>4. El administrador presiona "Guardar".<br>5. El sistema valida en el navegador que el texto sea JSON válido; si lo es, envía la actualización al backend.<br>6. El backend actualiza el registro y responde con el nuevo valor.<br>7. El sistema refresca la vista mostrando el valor y la fecha de actualización más recientes. |
| **Flujos alternativos / excepciones** | A1. El administrador no tiene el permiso "Editar configuración": el campo de valor se muestra en modo solo lectura y el botón "Guardar" permanece deshabilitado.<br>A2. El JSON ingresado es inválido: el sistema muestra la alerta "JSON inválido" y no envía la petición.<br>A3. El nombre del setting no existe en el backend: el sistema responde 404 y no aplica el cambio.<br>A4. No se envía un valor en la petición: el sistema responde 400 ("value is required"). |
| **Postcondiciones** | El valor del setting queda actualizado en la base de datos y es consumido de inmediato por la calculadora de plan de pagos diario, sin necesidad de reiniciar ningún servicio. La acción (éxito o falla) queda registrada en el log de auditoría del panel. |
| **Reglas de negocio** | `cutoffDates` define la lista de días del mes válidos como fecha de corte; `defaultCutoffDate` es el día de corte asignado por defecto a un cliente nuevo; `thresholdDays` es el umbral de días usado para decidir a qué fecha de corte se asigna un cliente según su fecha de aprobación. Toda modificación exitosa o fallida queda registrada en auditoría. |

| **Estado en plataforma** | **Implementado.** `GET /settings` y `PUT /settings/:name` (`settings.controller.ts`, `settings.service.ts`) están activos y la pantalla `apps/admin/src/app/settings/page.tsx` los consume. **Hallazgo técnico:** igual que en CU-030, la ruta `PUT /settings/:name` solo exige `authenticate` en el backend, sin validar el permiso `core:update-setting` a nivel de API. **Hallazgo adicional:** existe una constante `THRESHOLD_DAYS_SETTING_NAME` (`threshold_days`) declarada como si fuera un setting independiente, pero no se usa así en la práctica; el `thresholdDays` real vive anidado dentro de este mismo setting `cutoff_dates`. |
